# Compute capacity: optional offers and reservations

Aspen separates compute offers and physical-resource reservations from agent workers, membership placement and model routing. This is the optional compute-capacity boundary for [issue #42](https://github.com/brittonr/aspen/issues/42); its pure decision core is [`molten_core::compute_capacity`](../crates/molten-core/src/compute_capacity/mod.rs). Existing fabric membership CPU millis, memory bytes and storage bytes retain their meanings; a membership descriptor or placement recommendation is not an accelerator allocation. See [membership and placement](fabric-membership-placement.md) for its independent authority and lifecycle.

## Versioned authoring surface

[`config/compute-capacity/contracts.ncl`](../config/compute-capacity/contracts.ncl) defines the v1 Nickel `Offer`, candidate `Reservation`, versioned `Allocation`, `Readback`, `Consumer` and `Profile` authoring contracts. [`profile.ncl`](../config/compute-capacity/profile.ncl) selects logical time, bounds of 128 items and 256 ASCII identifier bytes, and mandatory non-claims. The offer and persisted-allocation labels are `molten.compute.offer.v1` and `molten.compute.reservation.v1`; the synthetic consumer and authoring profile are separately versioned. These Nickel inputs are checked authoring data, **not** the canonical Preserves codec, an admitted resource grant, or a live producer observation.

The strict public Preserves wrappers for offers and allocations are `compute-capacity-offer-v2` and `compute-capacity-allocation-v2`: they carry the captured observation cursor, charge cursor/time and exact activation evidence identity. `compute-capacity-readback-v1` remains a separate bounded projection. A v1 wrapper cannot be decoded as v2; this change has no shipped v1 store migration.

An offer binds host/device incarnation, provider/source profile, revision, topology generation, logical observation/expiry and charge cursor, health, label authority, compatibility and nonempty qualification references. Profile, qualification and grant references in positive fixtures have canonical `blake3:` plus 64 lowercase hexadecimal digits; their synthetic values assert only a valid reference shape, not independently verified provenance or live qualification. Each physical pool identifies its sole selected allocation authority and separately records physical total, policy-allocatable quantity, observed used/free and whether the observation already includes committed charges. `null` is unknown, not zero. An alias, partition, MMIO bundle, tray or mesh resolves to the same explicit physical pool identities; advertised view count never creates capacity. A view with `is_grouping_enforced = false` is unsupported for reservation, even if chip labels exist. Unknown backend/runtime/architecture/topology does not satisfy a required value; synthetic profile names and health labels are not provider qualification.

A reservation request binds current offer revision/incarnations, view/granularity, explicit claims on **every** backing pool, consumer/operation/attempt, owner generation and separately checked grant facts. Nickel can reject malformed, expired, mismatched or unsupported authored examples; the selected serialized owner must still recheck current grants, revocation, labels, capacity and observation basis, then persist intent **before** any backend activation. A duplicate matching operation returns the existing allocation without another charge. Shell persistence and effects are separate from pure `compute_capacity` transitions. On cancel, timeout, lost stop acknowledgement or disappearance, keep a charge/quarantine until the matching consumer and owner generation present affirmative backend-release evidence. Readback contains freshness, health, qualification refs, allocation owner/generation/granularity/status and logical fencing versus actual backend enforcement; it excludes secrets and backend handles.

The shell's `ComputeAdmissionPort` and `ComputeTimePort` must be wired to admitted grant/label and logical-time owners, not to request fields; the request's grant/clock values are ignored at the effect boundary. `Redb::open(root, authority_id)` pins the selected pool owner to that durable root; foreign-authority claims are denied before activation. Reconciliation queries the selected backend port read-only and accepts only matching evidence; an arbitrary caller cannot pass an activation or release assertion. A definitive backend no-effect refusal retires the intent only after a durable transition, whereas any possible effect remains charged. Offer observation charge cursors are captured when observed, not when delivered; charges newer than that cursor are debited even if observed free is already net of older charges. Released IDs remain in a bounded 128-record FIFO replay horizon; once evicted, an ID becomes unknown and can be admitted again under a new valid request, so external owners must use globally unique operation IDs beyond that horizon.

## Concrete synthetic consumer: agent A, serving B

The positive [two-host fixture](../config/compute-capacity/fixtures/positive/agent-a-serving-b.ncl) authors incompatible `cuda` and `unified` runtimes. Host A advertises dedicated device memory separately from host memory; host B advertises unified memory and one physical chip. At logical tick 20, `serving-b` claims 80/100 B shared-memory units and B's chip once as a **serving deployment**. Two independently identified agent executions, `agent-a-1` and `agent-a-2`, each claim 40/100 of A's host-memory pool through an agent execution view and reference the opaque `serving-b` allocation. Each A request charges only its A pool. B remains charged 80 memory units and one chip, **not** 160 units or two chips; releasing B while both A references remain is uncertain, not an implicit free. The [versioned allocation sample](../config/compute-capacity/fixtures/positive/serving-allocation.ncl) and [readback sample](../config/compute-capacity/fixtures/positive/serving-readback.ncl) show only an authored intent and logical fencing, not backend activation or model readiness.

The separate [synthetic Tenstorrent fixture](../config/compute-capacity/fixtures/positive/tt-overlap.ncl) authors one MMIO chip, an associated remote chip, a tray and two meshes sharing physical chip identities under one selected synthetic allocation owner. The second mesh is marked unenforced and its attempted reservation is a [negative fixture](../config/compute-capacity/fixtures/negative/unsupported-tt-mesh.ncl); labels do not invent qualified mesh support. These independently authored pools and views are examples, not observations from TT devices or assertions about a particular platform, firmware, driver, partition counter, or TT grouping. The [fixture-driven root tests](../src/compute_capacity/fixture/tests.rs) export the authored offers with Nickel, check pure-core eligibility and canonical records, then persist the TT MMIO and remote-chip charges through a supplied offer and Redb; overlapping tray/mesh claims fail rather than double-charge physical chips. [Duplicate physical-pool](../config/compute-capacity/fixtures/negative/duplicate-physical-pool.ncl), [expired offer](../config/compute-capacity/fixtures/negative/expired-offer.ncl), and [false live-qualification](../config/compute-capacity/fixtures/negative/false-live-qualification.ncl) inputs must fail contract evaluation. These synthetic tests do not exercise concurrent owner serialization or physical oversubscription; real adapter/restart and provider races require their own evidence.

The [missing observation](../config/compute-capacity/fixtures/negative/unobserved-free.ncl), [unknown runtime](../config/compute-capacity/fixtures/negative/unknown-runtime.ncl), [weak label authority](../config/compute-capacity/fixtures/negative/weak-label-authority.ncl), [noncanonical profile reference](../config/compute-capacity/fixtures/negative/noncanonical-profile-ref.ncl), and [empty qualification evidence](../config/compute-capacity/fixtures/negative/empty-qualification-refs.ncl) examples also fail; neither a missing free reading, unknown compatibility, advisory label nor invalid/absent evidence can satisfy a protected claim.

## Qualification and ownership limits

No live host/device inventory, TT grouping qualification, driver allocation, provider fencing, two-host request, model loading, inference readiness, KV/request budget, token quota or inference throughput has been established by these files. A healthy authoring offer and a synthetically valid grant are not permission to activate a workload. [Kiln #49](https://github.com/OnixResearch/kiln/issues/49) owns concrete host probes, backend process lifecycle, credentials and end-to-end host/inference qualification; [TT-Onix #44](https://github.com/OnixResearch/tt-onix/issues/44) owns TT host health integration. [Kiln #60](https://github.com/OnixResearch/kiln/issues/60) and [Lattice #24](https://github.com/OnixResearch/lattice/issues/24) consume owner/generation/granularity and execution facts without becoming the device allocation authority; [Animus #17](https://github.com/OnixResearch/animus/issues/17) owns serving request/readiness semantics. Actual cross-host transport and owner fencing require their separately scoped [#15](https://github.com/brittonr/aspen/issues/15) and [#20](https://github.com/brittonr/aspen/issues/20) qualification. The [capability qualification report](capability-qualification-report.md) cannot promote authored source fixtures into observed execution evidence.

Integration verification should export the profile and each positive fixture with the pinned Nickel CLI, require each negative fixture's export to fail, then run the focused core/shell and restart checks and applicable source/Cairn gates. None of those commands is an executed result recorded by this page; preserve exact source/build/profile and actual provider observations before any live claim.
