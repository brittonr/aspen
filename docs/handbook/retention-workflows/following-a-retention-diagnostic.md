# Following a retention diagnostic

Mode: Walkthrough

This walkthrough follows the checked-in `run_fixture` implementation, not a production deletion procedure. Its useful result is a small evidence chain: a protected reference is pinned, a destructive evaluation is denied, the fixture removes its own pin, and a later evaluation records a tombstone. It does not demonstrate physical erasure, remote clearance exchange, or the full GC plan/apply/execution/audit lifecycle.

All behavior below is source-checked, not executed for this handbook batch. The [technical companion](../../technical/world-effects/distribution-retention-and-reachability.md) explains why reachability and authority remain separate; here the task is to recognize precisely what each fixture artifact establishes.

## 1. Establish the fixture boundary

The concrete entry point is `run_fixture` in [retention part p025](../../../src/retention/parts/mod/p025/body.rs). It opens an artifact output root and a retention state root beneath that bundle, ensures the retention store exists, and creates deterministic synthetic references for an object, owner, policy, and evidence.

These are fixture identities generated by the implementation. They are not credentials, real object inventory, or evidence that a requester currently owns deletion authority. Do not copy synthetic values into an operational plan.

For an optional local exercise, choose a new, nonexistent output directory. The guard prevents accidental reuse; it does not add a CLI feature. Command spelling comes from the [root command declaration](../../../src/main/root/parts/command/p000/body.rs), [retention subcommands](../../../src/cli/workflow/retention/command.rs), and [argument declarations](../../../src/cli/workflow/retention/command/ops.rs); routing passes through [main aliases](../../../src/main.rs) and the [root dispatcher](../../../src/main/root.rs). Not executed here:

```sh
: "${RETENTION_FIXTURE_OUT:?Set a fresh isolated output directory}"
test ! -e "$RETENTION_FIXTURE_OUT" &&
  molten test retention run-fixture --out "$RETENTION_FIXTURE_OUT"
```

The command creates diagnostic state. It is not a read-only inspection of an existing live store.

## 2. Read the class and pin inputs

The fixture class is `private-secret-ref`, with minimum age zero, maximum age 86,400 seconds, secret-redaction and remote-GC-plan hooks enabled, and `can_compact` set true in its profile input. The pin names an `encrypted-ref`, source `secret-redaction`, and reason `private repro reveal pending`. It has no expiry reference.

The first observable boundary is the pin record plus its receipt: a named retention relationship now exists in the fixture store. The class profile is descriptive input, not a clock-driven expiration demonstration. In particular, the profile's `can_compact` field must not be read as overriding the evaluator's explicit private-secret compaction denial.

## 3. Follow the first destructive evaluation

The fixture evaluates action `delete` with a complete-index assertion, no separately supplied retained or remote references, and authority/clearance booleans set true. Nevertheless, the local reference index finds the active pin. [Evaluation diagnostics](../../../src/retention/parts/mod/p025/body.rs) add `active-pins-present`; [evaluation](../../../src/retention/parts/mod/p004/body.rs) turns nonempty diagnostics into a denied receipt.

This is the worked failure case: affirmative fixture authority inputs do not erase a pin. The important artifact is `delete-denied.preserves`, not a successful process exit or the presence of a receipt file. A diagnostic command can successfully write evidence of denial.

## 4. Observe the fixture-only transition

Next, the fixture invokes unpin with its synthetic requester, policy, evidence, and `has_authority: true`. The [unpin implementation](../../../src/retention/parts/mod/p003/body.rs) removes the stored pin when that input permits it and writes an unpin receipt. This walkthrough describes an internal fixture transition; it does not recommend unpinning operational state to obtain a passing result.

The following evaluation uses action `tombstone`. With that fixture pin gone and the remaining supplied inputs unchanged, the source path can build a passing retention receipt and tombstone. It does not invoke an object-store deletion adapter. A tombstone records a decision relationship, not proof that bytes vanished from every replica.

## 5. Match outputs to the question they answer

| Fixture output | Evidence to inspect |
| --- | --- |
| `retention-class.preserves` | Class-profile inputs used by this scenario |
| `pin.preserves`, `pin-receipt.preserves` | Historical pin and pin-operation receipt |
| `delete-denied.preserves` | Denied delete evaluation while the pin existed |
| `unpin-receipt.preserves` | Fixture's authorized unpin transition |
| `tombstone-receipt.preserves` | Later tombstone evaluation |
| `tombstone.preserves` | Tombstone when that evaluation produced one |

The saved `pin.preserves` remains historical output even after the active store pin has been removed. Do not confuse bundle artifacts with the current pin inventory. For a real candidate, continue with [inspecting pins before a GC plan](inspecting-pins-before-a-gc-plan.md), using genuine owner observations and scoped admissions rather than fixture booleans.
