# Following a catalog query

Mode: Walkthrough

This source-only walkthrough follows the checked-in `search_filters_schema_dependency_receipt_decision_text_and_visibility` fixture from installed values to a search result and then a hidden-result case. It does not construct a live registry, execute an artifact, or claim a test run. The fixture is in [catalog search tests](../../../src/catalog/parts/mod/tests/m000/p000/body.rs); the governing distinction between discovery and authority is explained in the [technical companion](../../technical/foundations/evidence-and-authority-separation.md).

## 1. Identify the two objects being searched

The fixture allocates an isolated registry and installs a `schema` artifact containing the Preserves value `<schema "search">`. Its schema reference is generated by the fixture helper, not obtained from a production schema registry. A second artifact has kind `receipt`, carries a `rewrite-receipt-v1` payload, and depends on the first artifact's full reference.

The receipt payload declares operation `apply` and decision `pass`. Those are fixture data. The setup does not perform a rewrite whose success this article could attest. The [installation helper](../../../src/catalog/parts/mod/tests/m000/p002/body.rs) additionally supplies generated effect, policy, evidence, installer, and capability references. These support local fixture construction; they are not reusable credentials.

**Observable boundary:** two installed artifact records with distinct canonical identities and an explicit dependency edge. A name, temporary directory, or Rust object address is not either identity. Architecture defines canonical Preserves bytes and BLAKE3 as the identity boundary.

## 2. Read the exact query input

The first query has no root restrictions, enables dependency and dependent inclusion, and uses four filters:

| Filter | Fixture value | Intended selection |
| --- | --- | --- |
| Artifact kind | `receipt` | Exclude the schema artifact |
| Dependency reference | Installed schema artifact's full ref | Select artifacts with that declared dependency |
| Receipt decision | `pass` | Match the represented decision |
| Text | `apply` | Match the public search representation |

Visibility is the default empty input. No ledger root is supplied. The [search entry point](../../../src/catalog/parts/mod/p000/body.rs) validates references, visibility, and filters before constructing a canonical query value. The query records scope, filters, rendering choices, and visibility inputs; filesystem roots remain shell inputs rather than canonical identity fields.

**Observable boundary:** a validated query description. The fixture's empty root list means the scope set is empty, which the search loop treats as unrestricted, not as “search nothing.”

## 3. Follow summary collection

[Summary collection](../../../src/catalog/parts/mod/p002/body.rs) lists registry artifacts, skips artifacts whose own references are hidden, optionally merges ledger entries, and sorts summaries by artifact reference. The optional ledger is absent here, so there is no ledger-only object to merge.

[Registry summaries](../../../src/catalog/parts/mod/p003/body.rs) include payload identity, schema and dependency references, reverse dependencies, effects, policy, evidence, classifications, and name-pointer references. They may read payloads for classification. Consequently, “summary query” means no artifact execution and no requested payload rendering; it does not mean payload bytes are never read internally.

**Observable boundary:** discoverable metadata. A classification is a search aid, not proof that the artifact's represented operation occurred or that its policy is currently applicable.

## 4. Apply the intersection of filters

The [filter implementation](../../../src/catalog/parts/mod/p006/body.rs) requires every filter to match. It does not combine these four criteria with OR. Dependency membership is checked against summary metadata. Receipt decision and text use the public text assembled from summary, artifact metadata, and redacted payload rendering.

The schema artifact fails the artifact-kind filter. The receipt artifact has the declared dependency and matching represented decision and operation. The fixture asserts one result. That is a checked-in assertion, not an observed execution result from this documentation batch.

**Observable boundary:** the selected summary, not the executable receipt payload and not permission to invoke a rewrite.

## 5. Distinguish the result from its evidence

`finish_query` hashes the query value, builds a `catalog-result-v1` value, hashes that result, and creates a `catalog-receipt-v1` binding the query and result. Its references also include hashes of returned item values. A summary item's hash is not interchangeable with the artifact reference inside that summary.

An ordinary completed search has decision `pass`, including a completed search with no items. That decision reports query completion, not artifact admission. The CLI separately renders items and emits receipt evidence; choosing a receipt output file adds a filesystem write even though catalog discovery does not mutate the registry.

## 6. Follow the negative visibility case

The same fixture searches for text `apply` again, but now puts the receipt artifact's full reference in `hidden_refs`. Collection removes that artifact before filtering, and the fixture asserts an empty item list.

Do not generalize this assertion into a complete confidentiality proof. It checks suppression of that artifact as a top-level result. Related summaries can contain dependency references, and direct views follow a different path. The [review checklist](reviewing-catalog-exposure-and-redaction.md) addresses these boundaries before external exposure.

The available stages are fixture setup, source-visible query processing, and source-visible assertions. Live storage access, adapter composition, execution admission, and runtime verification are outside this walkthrough. No command or test was executed for it.
