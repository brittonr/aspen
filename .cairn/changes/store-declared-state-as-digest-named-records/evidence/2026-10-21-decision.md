# Store declared state as digest-named records: consumer decision

## Decision

This package closes with the decision and no implementation. No admitted store of declared-interest
records needs multi-writer records today, and a digest-named layout without a consumer is
infrastructure the repository does not adopt.

The requirement `molten.durable_state_ports.digest_named_records` stays implementation-unestablished. The
tracey baseline already lists the `molten.durable_state_ports.*` requirements as accepted and
implementation-unestablished, and this change does not change that.

## Consumer census

The admitted node-state store is a capability-rooted filesystem with these namespaces
(`crates/molten-node-host/src/node/state/authority.rs`):

| Namespace | What it holds | Who writes it |
|---|---|---|
| `Identity`, `Secrets` | the node's identity and secret material | the node process at startup |
| `Ledger`, `Registry`, `Receipts`, `Chunks` | runtime state the node produces and reads back | the node process |
| `ControlInbox`, `ControlOutbox`, `ControlIngress`, `ControlIdempotency`, `ControlService` | per-request control traffic | the node process, one request at a time |
| `Services` | the node's service records | the node process |
| `Storage` | world commits, heads, merges, and distributions | the operator's CLI, as ordered world commits |

None of them is a store of declared-interest records:

- The control namespaces hold per-request traffic, not facts that owners add and withdraw.
- The identity, secret, ledger, registry, receipt, and chunk namespaces hold state the node derives, not declared
  interest.
- `Storage` is written by more than one process, but it holds ordered world commits rather than a set of
  independently declared facts, so a per-fact digest-named layout would not describe it.
- The operator's declared configuration is resolved into one aggregate profile
  (`src/node/profile/parts/config/p000/body.rs`), written by the operator, not by concurrent fact owners.

The nearest multi-process store therefore does not need the layout, and no other admitted store holds
declared-interest records at all.

## What the layout would have bought

A record-per-fact layout makes removal a single-file deletion, keeps unrelated owners intact, and makes
the file name a verifiable claim about the content. Those properties are real, and they are the reason the
manual recommends them. They are not needed by anything Molten admits today.

## What would reopen this package

An admitted store whose declared-interest records are added and withdrawn concurrently by independent
writers, with a merge rule that must not depend on file order or modification time. The layout, the
reader, and the fixtures in this package's design apply unchanged to that consumer.

## Non-claims

- No store was migrated, and no aggregate document changed.
- The content-addressed chunk store is untouched.
- No new authority, retention, or cleanup decision was introduced.
- The closed package is not a claim that the layout is wrong; it is a claim that no admitted consumer needs
  it yet.
