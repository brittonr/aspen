# Admit installed extensions to deterministic simulation

## Why

The existing scheduler and mechanism adapters are reusable, but world admission unconditionally requires semantic oracle rows for three closed reference systems. A collaboration or federation extension cannot truthfully satisfy those unrelated rows. Archiving the mechanism owner did not admit a new product consumer.

## Change

Add a separately admitted installed-extension world profile. It binds bounded node/workload rows to immutable extension core profiles and exact required invariant/handler identities from an explicit admitted registry. Missing, foreign, duplicate or wrong-handler bindings deny before scheduling. The scheduler, transport and durability mechanisms remain shared. No product-name exception, arbitrary string waiver, unchecked callback or fabricated reference oracle is introduced.

The initial accepted integration consumer is collaboration scope. Federated pull and node hosting may consume the same interface only with their own exact profiles, invariant handlers and execution evidence; their names grant no admission. Reference-world requirements and canonical projections remain unchanged.

## Scope and claims

The core validates loaded identities, linkage and finite bounds. Shells still acquire current authority, execute actual installed handlers and evaluate their admitted invariants. This proves neither handler correctness nor production admission. Parent approval authorizes this prerequisite; lifecycle checks, archive and publication remain parent-owned.
