## Context

`docs/octet-tigerstyle-remediation.md` records that current Octet evidence is clean but configuration-clean: `dylint.toml` disables broad/high-noise lint families such as file length, function length, repeated path segments, and module count. The archived `octet-tigerstyle-remediation` change deliberately did not claim source-remediated zero for those families.

`src/main.rs` is the largest imperative shell and is the best first target for incremental, behavior-preserving splits. The Octet command group was self-contained enough to move first because it depends mostly on `molten::octet_gate`, `molten::octet_remediation`, Preserves file IO, and receipt emission helpers. The Retention command group followed because it is operator-facing, self-contained around `molten::retention`, and large enough to materially reduce the monolithic CLI file while preserving receipt behavior. The Delivery command group is a smaller split around `molten::delivery_idempotency`; the Provenance command group follows the same low-risk pattern around `molten::provenance`. The Protocol command group is self-contained around `molten::protocol_session` and has existing CLI coverage. The Job command group is a hotspot split because its dispatch is large but remains a CLI shell over `molten::job_dag`, coordination scheduling evidence, local-gossip worker fixtures, and receipt IO. The Secrets and Plugin command groups are small low-risk follow-up splits over `molten::secrets` and `molten::plugin_host` fixture/install/show surfaces. The Node command group is the next top-level hotspot split over `molten::node_daemon`, `molten::node_runtime`, and provenance fixture helpers, including live workflow bundle diagnostics and node-control receipt materialization. The Repro command group is another test CLI hotspot split over harness repro export/verify/unpack and local Iroh repro exchange receipt materialization. The Catalog command group is a catalog/MCP hotspot split over `molten::catalog` and `molten::catalog_mcp` query, view, graph, short-id, chunk-store, and read-only MCP receipt surfaces. The Chunk command group is another hotspot split over `molten::chunk_store` put/verify/read/range/sync/local-Iroh/pin/index/receipt/lineage/GC receipt materialization. The Cache command group is a focused split over `molten::eval_cache` put/get/status/list/show/invalidate/index receipt materialization. The Artifact command group is a focused split over `molten::artifacts` install/list/view/name/dependency/closure/impact/index receipt materialization. The Storage command group is a focused split over `molten::typed_storage` put/get/recipe/migrate/verify receipt materialization. The Schema command group is a focused split over `molten::schema_identity` identity/alias/compat/search receipt materialization. The Upgrade command group is a focused split over `molten::upgrades` plan/create/name/task/rollback/status/cleanup receipt materialization. The Transcript command group is a focused split over `molten::transcripts` parse/run/show/render receipt materialization. The Rewrite command group is a focused split over `molten::rewrites` find/preview/apply/show receipt materialization and upgrade-plan handoff output. The Remote command group is a focused split over `molten::remote_dataspace` envelope, publish, deliver, two-peer harness, and gate receipt materialization. The Ledger/Chain command groups are focused splits over content-addressed ledger import/export/list/pin/GC and local Iroh evidence-chain publish/fetch receipt materialization. The Receipts command group is a focused split over operator receipt readback/export, signed receipt verification, and signed keyring import/list/show/revoke/rotate materialization. The Service command group is a focused split over service runtime, supervision, gate, replay, and fixture materialization. The Vat command group is a focused split over runtime vat fixture, snapshot, restore, promise, rights, distributed-ref, replay, authority-graph, portable-storage, and show materialization. The Coordination command group is a focused split over coordination manifests, requests, apply reports, fixtures, and bounded evidence materialization. The Dogfood command group is a focused split over local-node dogfood, Nix release evidence, release bundles, promotion gates, export archives, signed member verification, and summary materialization. The Raft command group is a focused split over control-registry fixtures, read-index evidence, snapshots, recovery receipts, and show summaries. The replay-fixture command group is a focused split over deterministic replay recording, verification, tamper receipts, rollups, indexes, and show output. The Report command group is a focused split over report show, validation, replay validation, and failure receipt materialization. The Gate command group is a focused split over pass-evidence gate checks, gate receipts, and artifact failure receipt materialization. The test Receipt command group is a focused split over signed pass-evidence receipt sign/verify helpers, reusing the receipt operator shell module. The harness Run/Replay handlers are the next focused split over suite execution, replay diagnostics, report output, and harness failure receipt materialization.

## Design

### CLI module boundary

Create binary-local CLI modules that own self-contained command groups:

- `src/cli/ops/octet.rs` owns `OctetCommand`, nested Octet subcommands, `run_octet_command`, and local Preserves file read/write helpers needed by Octet artifact, source-gate, baseline, review, gate, and remediation commands.

The CLI shell corpus now lives under bounded `src/cli/{core,workflow,ops,runtime,evidence,test}/` responsibility groups while retaining existing Rust module names through explicit `#[path = "cli/..."]` declarations in `src/main.rs`. Each group stays at or below the current module-file-count threshold, narrowing root `src/` module-count and underscore-filename burn-down pressure without a public CLI change.

The next source-layout slice moves underscore-named library/test source files into directory layouts while retaining public module names via explicit `#[path = "..."]` declarations in `src/lib.rs`, `src/harness/mod.rs`, and `src/runtime/mod.rs`. Examples include `src/job/dag.rs` for `job_dag`, `src/node/runtime.rs` for `node_runtime`, `src/octet/gate.rs` for `octet_gate`, `src/typed/storage.rs` for `typed_storage`, and `tests/cliharness.rs` for the integration test crate. This is a mechanical source-shape change only: public Rust paths, CLI syntax, canonical receipt schemas, and content-ref semantics remain unchanged. After the no-disabled-lints probe reports zero underscore-filename findings, `underscore_in_module_filename` is removed from `dylint.toml` while the remaining broad lint families stay explicit caveats.

The follow-on module-count slice converts the remaining broad flat modules to directory `mod.rs` layouts where public module names are already directory-friendly: `src/artifacts/mod.rs`, `src/ledger/mod.rs`, `src/resources/mod.rs`, `src/transcripts/mod.rs`, `src/upgrades/mod.rs`, and `src/runtime/{admission,bridge,config,dataspace,envelope,execution,predicates,spine,turn,vat}/mod.rs`. This keeps Rust item paths stable while eliminating Molten-source `module_file_count` findings. The no-disabled probe still reports `module_file_count` on external registry/rustlib files, so the family remains disabled until Octet/config/tooling can exclude those false positives or otherwise prove the source-scope requirement.

### Semantic preservation

The split must preserve:

- command paths and flags for `molten test octet ...`, `molten test delivery ...`, `molten test provenance ...`, `molten test protocol ...`, `molten test retention ...`, `molten test job ...`, `molten test secrets ...`, `molten test plugin ...`, `molten test repro ...`, `molten test catalog ...`, `molten test chunk ...`, `molten test cache ...`, `molten test artifact ...`, `molten test storage ...`, `molten test schema ...`, `molten test upgrade ...`, `molten test transcript ...`, `molten test rewrite ...`, `molten test remote ...`, `molten test ledger ...`, `molten test chain ...`, `molten test service ...`, `molten test vat ...`, `molten test coordination ...`, `molten test raft ...`, `molten test replay-fixture ...`, `molten test report ...`, `molten test gate ...`, `molten test receipt ...`, `molten test run ...`, `molten test replay ...`, `molten dogfood ...`, `molten receipts ...`, and `molten node ...`;
- receipt labels and stdout/stderr behavior;
- fail-closed denial errors for strict gate, source-gate validation, and baseline checks;
- canonical output values produced by the underlying core helpers.

The module may duplicate tiny shell helpers (`read_preserves_file`, `write_file`, `emit_named_receipt`) instead of depending on private `main.rs` helpers. This keeps the new module a CLI shell boundary and avoids moving unrelated repro/report helpers.

### Evidence and validation

Each slice should run focused Rust validation first, then refresh Octet evidence when the source scope changes materially. Module relocation slices must also update source-path inventories in the Octet remediation plan, source-gate docs, and object-corpus command list. Until disabled lint families are removed or narrowed, docs must continue describing the state as configuration-clean rather than source-remediated zero.

## Non-goals

- Do not change Octet gate policy semantics.
- Do not change canonical receipt schemas or refs intentionally.
- Do not remove disabled lint families until enough source splits have landed and Octet can validate the affected families without excessive false positives.
- Do not rewrite unrelated CLI command groups in this first slice.
