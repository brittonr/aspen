# Design: Repair runtime-spine SAM service Tracey links

## Success contract

A requirement leaves the baseline only when a specific production location and focused positive or negative test support its complete accepted wording.
Completion requires thirteen exact repairs, deterministic typed evidence, zero dangling markers, and repository validation.

False completion includes schema-name matching without parser tests, generic catalog redaction promoted to service classification, or process parentage promoted to logical supervision.

## Search registry

### Canonical service records

Review manifest, demand, status, supervisor, link, monitor, restart, lifecycle, and cleanup record builders and parsers.
Require stable BLAKE3 refs, explicit manifest boundaries, ledger classification, safe summaries, and malformed-record denial tests.

### Demand runtime

Review canonical suite admission, bounded dependency evaluation, pre-effect authority checks, owned readiness and status records, replay identities, and deterministic replay.
Require positive dependency startup plus missing-evidence, missing-dependency, cycle, malformed-record, and replay-divergence tests.

### Logical supervision

Review canonical links, monitors, failure propagation, restart decisions, scheduled demands, lifecycle receipts, and replay.
Require process-parentage denial and deterministic monitor-order tests.

### Cleanup and retention

Review owned-state indexes, bounded restart policy, retractions, cleanup receipts, retention inputs, and replay gates.
Require revocation, resource denial, restart exhaustion, foreign-state denial, cleanup-divergence, and bounded property tests.

## Evidence manifest

A typed Nickel manifest records each identifier, source area, implementation path, verification path, and bounded evidence scope.
Generated JSON is a deterministic validation input.

## Freshness gate

The inherited Tracey Nix check exports the new manifest, compares generated JSON, checks exact and unique identifiers, verifies each declared marker path, and rejects any repaired identifier that remains in the baseline.

## Functional boundary

The patch adds marker comments and evidence metadata only.
Production behavior and test assertions remain unchanged.

## Non-claims

The repair does not grant ambient service authority, accept operating-system parentage as supervision, bypass retention policy, establish complete runtime-spine coverage, establish release readiness, or prove whole-system correctness.
